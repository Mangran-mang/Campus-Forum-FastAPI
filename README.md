# 漫燃社区 · 校园论坛

面向高校的社区平台：板块讨论、二手交易、实时私信，举报内容由 AI 初审。
后端全异步（FastAPI + SQLAlchemy 2.0 async + MySQL + Redis），前端 Vue 3 + ECharts。

**在线地址**：[https://zcfe.online](https://zcfe.online)

---

## 一、这个项目解决什么

校园里的信息天然是散的：课程通知在班群、失物招领在朋友圈、二手书在另一个群，刷过去就找不回来了。想做的是一个**有结构、有治理**的校园社区 —— 内容按板块归档、有人管、能私聊成交，外加一个给运营者看数据、管内容的后台。

它不是一个"教程式 demo"：65 个接口、15 张表、从认证到内容审核到数据看板都是围绕真实使用场景做的，**每个设计点都有明确的取舍理由**（见第六节）。

## 四、项目结构

```
├── routers/      # API 路由层（14 个模块，64 个 HTTP 端点 + 1 个 WebSocket）
├── crud/         # 数据访问层（只返回 ORM 对象，序列化归 router）
├── models/       # SQLAlchemy 模型（15 张表）
├── schemas/      # Pydantic 请求 / 响应模型（含统一信封 Envelope[T]）
├── ai_agent/     # 内容审核（通义千问）
├── tools/        # 认证依赖、统一异常、日志、WebSocket 连接管理、中间件
├── config/       # 配置、数据库 / Redis 连接
├── migrations/   # Alembic 迁移（18 个版本）
├── tests/        # pytest 单元测试（50 条，不依赖数据库）
└── frontend/     # Vue 3 前端
```

## 五、本地运行

需要预先准备好 MySQL 与 Redis 实例。

```bash
# ---- 后端 ----
python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.lock

cp .env.example .env               # 填入数据库 / Redis / JWT 密钥 / AI API Key
cp alembic.ini.example alembic.ini
alembic upgrade head               # 建表

uvicorn main:app --reload          # http://127.0.0.1:8000（/docs 是自动生成的接口文档）

# ---- 前端 ----
cd frontend
npm install
npm run dev                        # http://127.0.0.1:5173
```

> 前端 dev server 已配置 `/api`、`/uploads`、`/ws` 的反向代理，目标写死为 `127.0.0.1:8000` —— 本地起后端时端口别改。

## 六、设计要点

每条都写成**「问题 → 方案 → 为什么」**，因为"用了什么技术"没有意义，"为什么这么选"才是。

### 1. 统一响应契约，而不是到处手写字典

**问题**：接口多了以后，成功返回 `{...}`、失败返回 `{"detail": "..."}`、校验失败又是另一种格式，前端每接一个接口都要重新适配。

**方案**：全站三层信封 `{code, message, data}`，由 `success_response()` 统一产出，**64 个 HTTP 端点全部挂 `response_model=Envelope[T]`**，路由层禁止手写字典或 `JSONResponse`。

**为什么**：关键认知是 —— `success_response` **只负责包装，不过滤**；真正决定"哪些字段能出网"的是 `response_model`。所以它不是文档装饰，而是**输出白名单**：把 `UserOutModel` 挂上去，password 哈希就永远出不去。另外 `response_model` 校验的是**整个信封**（不只 data），字段名对不上是直接 500 而不是静默丢数据。

### 2. 认证：双 Token 轮换 + 哈希落库 + 黑名单

**问题**：JWT 天生无状态，"登出"和"续期"都不好做；长效凭证一旦泄露就是长期肉鸡。

**方案**（四件事叠起来）：

| 措施 | 解决的问题 |
|---|---|
| Access 短（1h）+ Refresh 长（2d） | 兼顾安全与体验：短期凭证泄露窗口小，长期凭证负责无感续期 |
| Refresh **轮换**（用一次换一把，旧行立刻失效） | 防 replay：偷到的旧 refresh 在你之前用过就废了 |
| Refresh **只存 SHA-256**（库里是哈希，前端拿的才是明文） | 数据库被拖走也无法直接复用；JWT 是高熵随机串，快哈希足够（不需要 bcrypt 的慢哈希 + 盐） |
| JTI 黑名单（Redis，TTL = 剩余寿命） | 补上 JWT 无状态缺的那一环：登出立即失效，且条目与 token 同时"死亡"，不占长期内存 |

**还额外防了两件事**：登录失败时，**非管理员 / 密码错 / 邮箱不存在一律返回同一句「邮箱或密码错误」**（防用户枚举），且用户不存在时也跑一次等价的密码哈希计算（`DUMMY_HASH`）把响应时间对齐（防时序侧信道）。

### 3. 后台为什么不签 Refresh Token

**问题**：管理入口和用户前台，安全模型一样吗？

**方案**：不一样。后台**只签发 1 小时的 Access Token，不签发 Refresh**，过期就重新登录；前后台使用**独立的本地存储键**，会话完全解耦。

**为什么**：Refresh 轮换机制存在的意义是"长效凭证的安全复用"。而管理员用后台是**短时间集中处理**，不是全天挂着 —— 直接砍掉长效凭证，泄露窗口从 2 天缩到 1 小时，代价只是"偶尔重登一次"。同时因为前后台会话独立，**前台登录状态下进 /admin 仍需单独登录一次**（step-up authentication），这也是云控制台的一贯做法。

### 4. 异步 ORM 的两条纪律

**问题**：SQLAlchemy async 有两个"不报错但会炸"的坑 —— 异步懒加载（`MissingGreenlet`）和 N+1 查询。

**方案**：

- **预加载纪律**：只要输出模型的声明链上出现关系字段（哪怕 router 代码没读它），crud 就必须显式预加载 —— 因为 pydantic 是**声明式取值**，它会对全部声明字段取值，而这会触发异步懒加载。
- **统计用相关子查询，而不是 join + group by**：给列表每行附上"发帖数 / 评论数"这类聚合时，用 `scalar_subquery` 而不是连接后分组 —— 后者会因行复制导致分页错乱，且没数据的行会整行消失。多条标量子查询还能拼进**一条 SQL、一次往返**拿到多个统计值。
- 分页统一 clamp（`page ≥ 1`、`page_size ≤ 上限`）+ 显式 `order_by` + 把生效值回显给前端。

### 5. WebSocket 私信：从轮询到长连接，以及长连接的代价

**问题**：最初用轮询实现私信，延迟与服务器压力都不可接受；换成 WebSocket 后，又发现**长连接会把 HTTP 共用的数据库连接池吃光**。

**方案**：

- 自建 `ConnectionManager` 管理 `user_uid → 连接` 的注册表，支持点对点推送。
- **短会话设计**：连接持有数据库会话的时间，从"页面打开的整段时间"压缩到"单次 SQL 的耗时" —— 请求即取即还，长连接不再占着连接池。
- **逐条容错推送**：广播时单个失效连接不能让整轮推送中断（否则会留下僵尸连接）。
- 前端配合做**指数退避重连** + 重复建连守卫 + 断线消息回填。

### 6. Redis 的三个用法，三种数据结构

用 Redis 不等于"用缓存"。这个项目里它承担三件性质完全不同的事：

| 用途 | 结构 | 关键点 |
|---|---|---|
| JTI 黑名单 | String + TTL | TTL 设为 token 剩余寿命，条目与凭证同生共死 |
| 举报去重 | String `SET NX EX` | **一条命令完成"检查 + 写入"**，天然原子，绕开 check-then-act 竞态 |
| 日活统计 | Set + TTL | 集合**天然去重**：同一人访问 100 次仍是 1 个成员（这是 UV，不是 PV）；`SADD` 的返回值（1 = 首次）用来判断"今天第一次来"，**只在首次设 TTL**，避免每个请求都多发一条 `EXPIRE` |

**为什么日活用 Set 而不是 HyperLogLog**：HLL 的优势是省内存（固定 12KB），但在校园体量下毫无意义；而 Set 保留了 `SINTER`（交集）能力 —— 想算"昨天来过的人今天还回来多少"（次日留存）时，一条命令就出来了，HLL 永远只能给一个数字。

**为什么不用 Redis 计数器（INCR）**：那统计出来的是 PV（访问量），不是 UV（独立访客）。

### 7. 数据看板：接口形状为图表而设计

**问题**：统计接口返回"行式"数据（`[{date, count}, ...]`），前端要拆两列才能喂给图表；而且看图时会踩三个坑。

**方案与坑**：

| 坑 | 处理 |
|---|---|
| 分组查询只返回**有数据的天**，缺天会让折线直接断掉 | 后端按天序列**补零**，前端拿到就能画 |
| 帖子可能没有板块（`category_id` 为 NULL），`INNER JOIN` 会让这些行**整行消失**，饼图各扇区加起来 ≠ 总数，且不报错 | `outerjoin` + `COALESCE(name, '未分区')`，让它们归入"未分区"，**总数守恒** |
| 入参无上限：`?days=99999` 会让补零生成近十万个元素（4MB 响应） | 参数 clamp，并在 crud 层兜底（不只依赖路由层校验） |

接口直接返回**列式**结构（`{dates: [...], values: [...]}`）—— 正好对应 ECharts 的 `xAxis.data` 与 `series.data`，前端零转换。

**前端分包**：ECharts 按需引入（只注册用到的图表与组件）后仍有约 180KB(gzip)，**若静态引入会让前台用户为完全用不到的后台图表买单**。因此后台 6 个页面全部改为路由懒加载，主包维持在约 197KB，图表依赖只在访问看板时加载。

### 8. 工程化细节

| 项 | 做法 |
|---|---|
| 异常体系 | `APIException` 基类 + 业务异常子类 + 框架异常统一注册 handler，业务代码只负责 `raise`，不手写响应体 |
| 日志分级 | 4xx 记 warning、5xx 记 exception —— 判据是"这件事需不需要人来看" |
| 迁移治理 | MySQL DDL 非事务，迁移写成**幂等**（先查 `information_schema` 再决定建不建）；外键与索引调整有固定顺序（先建新索引再删旧、外键两端类型必须严格一致） |
| 单元测试 | 50 条，覆盖安全原语（密码哈希 / JWT）、查询构造（LIKE 转义）、异常处理；**不依赖数据库、不起服务**，2.5 秒跑完 |

## 八、注意事项与已知限制

如实记录，避免后来者（包括我自己）踩进去：

1. **多进程部署有盲区**：WebSocket 的连接注册表是**进程级**的，多 worker 下会丢推送；同时连接池也会随进程数翻倍。所以 `--workers` 保持为 1。
2. **WebSocket 请求不走 HTTP 中间件**（scope 不同），因此"只挂着私信页面聊天"的用户不会被计入日活 —— 属已知取舍。
3. **日活只保留最近 2 天**：Redis 里日活 key 的 TTL 决定了历史深度，接口的查询上限与之对齐。要更长的历史，需要定时把每日 UV 落到数据库。
4. **日活有冷启动**：埋点上线前的日期没有数据，趋势上表现为 0，这是"数据不存在"而非"那天没人活跃"。
5. **趋势查询依赖 `created_time` 索引**：数据量增长到一定规模后，按天分组统计应改为预聚合表（或引入专门的分析库），而非每次实时聚合。
6. **前后台会话独立**：同一浏览器可同时保持前台与后台登录态，互不影响（这是刻意设计，不是 bug）。
7. **AI 审核是辅助而非终审**：判定结果会直接删帖，因此保留了人工复核的空间；AI 服务不可用时走降级逻辑而不是阻塞发帖。
