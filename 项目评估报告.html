① 代码规范程度

7.0

✓ 做得好的

  • 六层结构（routers / crud / models / schemas / tools / config）严格执行，13 个业务模块一一对应，按目录即可定位功能

③ 数据库索引优化的大概水平

4.0

✓ 做得好的（缓解因素）

  • 查询层意识不错：列表页 selectinload 预加载避免 N+1；分页 limit/offset；计数与列表拆成两条 SQL
  • 现有索引全部来自「免费」来源：主键、user.email 唯一约束、likes(post_id, user_uid) 联合唯一、MySQL InnoDB 为外键自动建的列索引——单列等值查询尚有覆盖
  • 当前校园规模数据量小，问题尚未暴露

✗ 不足（热查询与索引不匹配）

  • 全部 17 张模型没有一处显式索引（index=True 与 Index(...) 均无，已全局搜索确认）
  • 帖子列表按 is_top DESC, created_time DESC 排序（crud/posts.py:53）→ 全表扫描 + filesort
  • 通知中心高频查 (recipient_uid, is_read) + 时间排序、未读计数（crud/notification.py:85），缺 (recipient_uid, is_read, created_time)
  • 私信消息缺 (conversation_id, created_time)；图片表缺 (target_type, target_id)；商品缺 (author_uid, status)；楼中楼缺 comments(parent_id)
证据：属于「零主动索引设计」水平。帖子列表、通知、私信三类页面在十万行级会明显退化；好在补救成本低——一次性补 5~6 个复合索引，走 Alembic 迁移即可。

④ 模块解耦程度

7.0

✓ 做得好的

  • 依赖方向健康：routers → crud → models，传输结构由 schemas 隔离；main.py 63 行纯装配（路由/异常/中间件注册一眼可读）
  • 横切能力沉淀在 tools 层（认证、异常、日志、WebSocket 连接管理），通知服务被点赞/评论/举报多模块复用，AI 审核独立成 ai_agent 包
  • 经验值/等级更新与发帖、评论放进同一事务（crud/posts.py:21-25 先 flush 后 commit，注释明确设计意图），事务意识超出学习项目平均水准

✗ 不足

  • crud 层反向依赖 Web 框架：直接 raise HTTPException（crud/user.py:38、crud/posts.py:101）——已有 UserException/PostException 体系却未贯彻，换框架或写 CLI 脚本时全部要重写
  • 部分路由越层：routers/posts.py:76-80 在路由里直接改 view_count 并 commit；routers/posts.py:93 手动二次调用 get_user_by_token 绕过依赖注入体系
  • ConnectionManager 把 WS 连接存进程内存字典，与多 worker 部署隐式冲突且无任何文档标注——多进程下推送会静默失效
证据：边界在多数场景真实生效（schemas 隔离、tools 复用），但数据层对 FastAPI 的依赖是系统性选择而非个别疏漏，属于「分层执行到位、边界纪律不稳」的典型形态。

5.5

✓ 做得好的

  • 全局异常体系完整：APIException 基类 + 五个子类，MRO 一次注册全覆盖；422 重排为 {field, message} 方便表单回显；DB 异常只回传结论性文案，原始 SQL 只进日志

  • 零自动化测试：全仓库无 test_*.py，回归全靠手工点测

  • 同步 AI 调用阻塞事件循环：2~5 秒的 review_model.invoke() 直接跑在 async 路由里（routers/posts.py:141），单个举报卡住整个服务
  • 浏览量读-改-写非原子（并发丢计数）且在 GET 里 commit；资料更新把密码明文落库破坏后续登录；WS 握手对会话不存在无防护（conv.user_b_uid 直接 AttributeError）；登录无限流
证据：更新日志所称「所有接口完成测试」实为人工点测。权限写反这类错误恰好是单测最该兜住的对象——健壮性的最大短板不是写错某一行，而是没有任何网防止住已写错的行。

⑥ 用户信息安全性

5.0

✓ 做得好的（超出学习项目平均水准）

  • 双 Token 体系完整：access 1h / refresh 2d、类型互斥校验（拿 access 调刷新接口会被拒）
  • refresh 轮换 + SHA-256 哈希落库（2026-09-04 改造）：库里绝不存原始 token，轮换时旧 refresh 因哈希比对失败自动作废，泄露凭证只有一次利用窗口；注释完整论证 bcrypt vs SHA-256 的取舍
  • JTI + Redis 黑名单让登出立即生效；统一异常处理器确保 SQL 细节/堆栈不回传前端；.env 不入库
  • 图片上传安全五件套：MIME 白名单、Content-Length 预检 + 流式限额、Pillow 重编码（杀伪装载荷）、UUID 重命名 + 子目录、数量与属主校验

✗ 不足（按风险排序）

  • 高危 · 密码哈希随响应泄漏（已运行验证）：帖子/评论/商品路由直接返回带 selectinload(author) 的 ORM 且无 response_model——实测 jsonable_encoder 输出中作者的 password 哈希与 email 原样下发给任何登录用户
  • 高危 · mass assignment 自助提权：注册/更新模型暴露 is_superuser，crud 直接 User(**model_dump()) / 逐字段 setattr——请求体带 "is_superuser": true 即成管理员
  • 中危：WebSocket 握手只验签名——不校验 refresh 标志（refresh token 可建连）、不查 JTI 黑名单（已登出 token 仍可收发私信）
  • 登录无限流可暴力尝试；/api/user/all 向管理员返回全量用户邮箱（有权限门但宜脱敏）
证据：用项目 venv 实测序列化行为： 
POST KEYS:  [..., 'author', 'author_uid', 'content', ...]
AUTHOR KEYS: ['created_time', 'email', ..., 'password', ...]
PASSWORD LEAKED: True  'HASHED_SECRET'
讽刺的是 routers/message.py 的 _user_brief() 已有正确的白名单序列化示范，只是没有推广到其余模块。认证架构本身的实现质量很高，扣分集中在「最后一公里的输出过滤」。

✓ 做得好的

  • 日志基建完整：RotatingFileHandler（10MB×5 滚动）+ 控制台双通道；HTTP 访问日志记录 IP/方法/路径/状态码；异常分级合理（4xx warning、5xx 全堆栈 logger.exception）
  • 更新日志.md 按日持续维护 3 个月+，记录的是「为什么这么改」（token 轮换的取舍、双标签页 401 的代价），对未来回溯设计决策价值极高

⑧ 项目含金量

6.5

✓ 做得好的

  • 真实生产部署闭环：域名 zcfe.online 在线运行，腾讯云 + Nginx + HTTPS + systemd——绝大多数同类项目止步于本地跑通，「敢上线并维护着」本身就是稀缺信号
  • 外部集成是真实打通而非 Mock：通义千问 AI 审核（真实 API + 失败降级人工）、MySQL、Redis、WebSocket 全是真实链路，AI 自动审核举报 + 违规帖自动处置是功能差异化亮点
  • 功能广度大且持续演进 3 个多月：论坛（板块/楼中楼/点赞/收藏/通知）+ 二手交易 + 实时私信 + 等级经验体系，更新日志从 5 月写到 9 月，不是一次性作业
  • 认证组合（轮换 + 哈希落存 + 黑名单 + 防时序）是面试可讲深入的差异化素材，远超「jwt.encode 一把梭」的普遍水平

✗ 不足

  • 业务域高频撞题：校园论坛是全栈教程与 AI 生成项目的第一大题材，技术栈全主流（FastAPI + Vue3），选题本身无稀缺标签
  • 零自动化测试拖累「完成度」叙事：作品集场景下无法自证质量；「所有接口完成测试」实为人工点测，说服力有限
  • 两个已验证高危漏洞（哈希泄漏/自助提权）说明「最后 10% 的打磨」未完成；README 命令与实际文件名不符等文档瑕疵进一步减分
  • 前端为标准 Vue3 SPA，无亮眼技术标签（无可视化、无性能专项、无算法类内容）
证据：含金量评的是「相对同类作品的位置」。上线闭环、真实 AI 集成与认证深度把它抬到同类平均线之上；选题高频、无测试、安全收尾未完成又封住了上限——处于「比大多数课程设计强、离能写进简历 top 项还差一步」的区间。

⑨ 项目深度

6.0

✓ 做得好的（深度体现在已啃下的硬骨头）

  • 真正解决了「JWT 无状态 vs 登出吊销」的矛盾：jti 黑名单 + 单行轮换（覆盖即作废）+ 哈希比对，并论证了高熵 token 用快哈希、低熵密码才用 bcrypt——这是全仓库最深的一块，且踩坑迭代痕迹真实（9/3 哈希落存 → 9/4 轮换补齐）
  • 若干正确的并发细节：Redis SET NX EX 原子去重（举报防重）、经验值原子 UPDATE 防读改写丢失、上传流式限额边读边断、压缩丢 to_thread 不阻塞
  • 全链路 async（SQLAlchemy async + aiomysql）+ WebSocket 真推送私信，不是轮询模拟

✗ 不足（深度上限评估）

  • 问题面整体在「框架追随」层：无全文搜索（LIKE 模糊匹配）、无缓存策略（热帖/通知计数均直查 DB）、无排序算法（置顶 + 时间二段排序）、无压测与高并发设计
  • 异步理解有一处明显裂缝：同步 AI 调用直接跑在 async 路由里阻塞事件循环 2~5 秒，与「全异步架构」的自我定位矛盾——说明对事件循环的代价模型理解不完整
  • 横向扩展能力为零：WS 连接存进程内存、无共享状态；复合索引缺位说明对查询规模化的思考停在单表量级
证据：深度分评「问题难度上限」而非实现质量（实现质量见维度⑤）。最难的三个点——token 生命周期、WS 实时通讯、上传管线——完成度都不错，但没有任何一处进入需要自行设计算法或权衡未知方案的领域；事件循环阻塞与索引缺位暴露了深度分布的不均匀。
